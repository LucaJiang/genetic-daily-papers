# 用 GPT Astra 复现自己的研究论文与数据网站

本指南适合希望沿用本站结构、改为收录自己研究领域的人。目标是得到一个可维护的 Astro 静态网站：论文精读页、按日期归档的刊期、主题导航、数据资源目录、搜索，以及可核对的文献和图表来源。

复用代码可以得到相似的网站结构；选文质量还需要你提供研究问题、正反例和反馈。以下是针对本仓库编写的工作提示词，不是 OpenAI 官方模板，也不保证一次对话就能得到完全一致的结果。

[返回 README](../README.md)

## 1. 开始前准备什么

在你有权使用 GPT Astra 的环境中选择该模型，并让它能读取**你自己的 fork 或新仓库**。网页检索、PDF 阅读、文件编辑、构建、GitHub 写入和部署能力取决于使用环境及已连接的工具；模型名称本身不代表这些权限已经具备。没有 GitHub 写入能力时，可以先让它交付修改文件或补丁，再由你提交。

准备下面的信息。不确定的项可以写“请提出建议”，账号凭据和访问令牌不要放进提示词或仓库。

| 信息 | 怎么填写 |
| --- | --- |
| 核心研究问题 | 按优先级写 3–5 个具体问题；说明关注方法、机制、应用还是数据 |
| 正例 | 给 3–5 篇真实论文的 DOI、链接或 PDF，并各写一句为什么值得收录 |
| 反例 | 给 2–3 篇或几类看似相关却不该收录的文章，说明缺少哪种联系 |
| 邻近方向 | 哪些可以纳入，以及必须满足的具体条件 |
| 数据目录 | 需要什么资源，按哪些字段比较；哪些是公开数据，哪些只能记录元数据 |
| 阅读方式 | 目标读者、语言、技术深度、是否解释公式、希望精读哪些结果 |
| 时间规则 | 时区、最近几天、是否收预印本、是否允许明确标注的旧文补读 |
| 网站与仓库 | 自己的仓库 URL、站名、目标域名、托管平台、生产分支 |
| 示例内容 | 在自己的 fork 中替换原站遗传学示例，还是明确标为演示并保留 |

例如，“电池寿命预测”可以进一步写成：重点关注跨工况泛化和不确定性评估；仅有电池关键词、却不涉及寿命预测的文章不收；数据目录要区分独立电池数量与循环记录数，记录实验条件、数据划分、版本和访问方式。这只是填写方向的示例，正例论文仍应由你提供真实来源。

## 2. 可直接复制的开场 Prompt

把所有 `【……】` 换成你的信息后，将下面整段交给 Astra。可以同时附上论文 PDF、已有文献清单和公开数据链接；先说明每个附件的用途。

```text
请以 https://github.com/LucaJiang/genetic-daily-papers 为参考，
在我自己的仓库中实现一个面向我的研究领域的论文精读与数据资源网站。
请实际完成已授权的研究、文件修改和验证，并通过分阶段交互交付结果。

【项目目标】
我的仓库：【自己的仓库 URL；若尚未创建，先给出建仓步骤】
站名：【名称】
目标域名与托管方式：【自己的域名、托管平台；未定则先做本地预览】
生产分支：【分支名；不确定时检查仓库和托管配置】
读者与语言：【读者背景；中文或其他语言；技术深度】
我希望沿用：论文独立页面、按日归档、主题导航、数据资源目录、
全文搜索、公式、原文图表及其来源、桌面与手机阅读体验。
默认在我的 fork 中替换原站的领域示例；保留代码许可证和原有版权声明。
如目标仓库已有我自己的正式内容，请保留，迁移前先检查现状。

【研究画像】
核心问题及优先级：
1. 【问题一及为什么重要】
2. 【问题二】
3. 【问题三】
可纳入的邻近方向与条件：【内容】
正例论文及理由：【真实 DOI / 链接 / 附件；每篇的相关性】
反例及排除理由：【文章或类别；为什么不符合我的问题】
方法、应用、数据资源的偏好：【内容】
期刊或来源偏好：【内容；相关性优先，不只看期刊或关键词】
预印本政策：【收录并注明版本 / 暂不收录】
检索窗口与时区：【例如最近 7 天；Asia/Shanghai】
旧文补读政策：【允许并标注 / 不需要】
数据资源范围与比较字段：【数据类型、独立样本单位、规模、版本、
适用场景、获取方式、许可证等；按我的领域调整】
公开边界：【可公开内容；仅供选题参考、不得写入仓库或网站的材料】

【工作方式】
先读取目标仓库的 README、AGENTS.md、研究画像、内容 schema、
页面与搜索代码、验证脚本和部署配置，核对当前分支及未提交改动。
原站的研究方向和写作偏好只是迁移起点，按我明确提供的画像调整；
保留来源核验、隐私、发布状态和构建检查等通用要求。
不要沿用原站主的个人身份、域名或研究经历，也不要向参考仓库提交。

先用一段话复述收录标准，给出第一批候选和纳入／排除理由，
让我确认选题。候选最多 6–10 篇，找不到足够相关的可以更少或为零。
列出标题、原始链接、发表／版本日期、文章类型、相关性、
已经读到的材料范围，以及需要我补充的全文。
同时完成不依赖选题确认的仓库检查和迁移准备。

对于可逆的日常实现选择，按合理默认继续；真正影响选题、
公开范围或部署目标的缺失信息，一次集中问不超过 3 个问题。
沿用我已给出的确认，不要对同一项工作重复请求许可。
如果环境有子代理，可并行做独立的候选检索、全文核查或代码审查，
最后统一核对来源、合并结果并处理冲突。

【内容要求】
我确认选题后，再完成精读和网站内容草稿。
优先阅读原始论文、相关方法、补充材料及数据说明。
明确区分只读了摘要、读了正文、读了补充材料；
全文不可得时先完成可核实部分，并告诉我具体需要哪些 PDF。
不能根据摘要补写方法、数字、消融实验或图表结论。

每篇解释研究问题、方法与关键假设、真实数据和比较设置、
主要结果、具体局限，以及与我的研究问题的联系。
区分作者报告的结果和你的推论。数字应能追溯到表格、
图号或正文位置；不要把相关性、预测能力和因果证据混为一谈。
使用准确、自然的领域语言，避免宣传句和每篇通用的空泛批评。
论文发表日期、预印本版本日期、数据发布日期和网站刊期分别记录；
不要把旧论文包装成今天发表，也不要为了凑数量收录弱相关文章。

选择有助理解结果的原文图，核对图号、版本、来源和复用条件，
在相应分析段落旁引用。本地图片文件、说明和来源必须一致。
不要生成或依据文字重绘实验结果；无法取得可用原图时说明缺口。
公式按仓库的 Markdown / KaTeX 方式编写，并检查实际渲染。

数据资源逐项给出原始来源、版本、规模及单位、获取方式、
访问限制、许可证或其状态、用途和局限；未核实的字段明确标注。
区分数据集、论文、软件和下载门户，避免重复统计同一数据。
默认只发布我同意公开的资源元数据和链接，不上传原始研究数据。

【领域迁移与实现】
同步修改研究画像、选题规则、主题、站名、域名、论文和刊期，
并将资源 schema、筛选维度、页面和搜索改为适合我的领域。
当前 QTL 专用字段不能只改显示名称后继续套用。
检查脚本中写死的遗传学论文、日期、数量、搜索词和旧标题规则：
替换为新领域的真实验收样例，保留通用验证，不能删除检查来求通过。
清理自己 fork 中被替换的示例引用和不再使用的图片，避免破坏共享资源。
把我确认的规则写入研究画像及相关说明，后续不依赖聊天记忆。

【审阅与发布】
先在工作分支交付内容和实现；新论文与刊期保持 published: false。
当前正常构建不会展示这些草稿。审阅时使用不提交、不推送的隔离本地
预览副本，临时启用本次论文及刊期后构建，检查新稿图片、公式与搜索；
不要把临时发布标记带回待审分支。也可实现与生产构建隔离的草稿预览。
不能用排除了新稿的构建，声称新稿已经通过页面和图表检查。
当前资源 JSON 没有逐条草稿开关：未确认的资源放在不被页面和搜索
读取的草稿文件中，或者先实现并验证资源的发布控制。
在我授权公开之前，不推送到会自动部署生产站的分支，
不合并到生产分支，也不发布到公开托管环境。
如果工作分支会自动生成公开预览，也要先核对公开范围。

提交审阅时说明修改了什么、原文依据、待确认问题和验证结果。
在发布前完成实际构建、必要的内容／搜索／链接检查，
并检查代表性的桌面与手机页面、图片和公式。
不能运行的检查如实说明，不能宣称已经通过。
得到我对明确内容和部署目标的发布指令后，继续执行到部署结果核实，
不要把提交成功或 CI 成功直接当成网站已上线。
默认不开启定时搜论文、自动生成或自动发布任务。
```

这段 Prompt 的作用是建立任务边界和质量标准。第一次先审研究画像与候选，第二次审实际内容和预览；普通实现细节交给 Astra 继续完成。你也可以在开场时直接指定已选论文，省去候选筛选这一轮。

## 3. 后续怎么和 Astra 对话

不需要每轮重贴长 Prompt。说明具体对象、变化原因和下一步动作即可。

### 校准相关性

```text
保留候选 1、3、5。第 2 篇虽然用了【某个关键词】，但没有解决
【我的核心问题】，这次不收。第 4 篇的方法可用于【具体问题】，可以补读。
请把这些理由补充到研究画像和选题规则，不要扩大成对整个方向的排除。
按修正后的标准补充候选，先不发布。
```

指出“为什么不相关”比只说“不喜欢”更容易让下一轮筛选改善。种子论文用于说明方法兴趣，不应变成只追踪某个作者或实验室的名单。

### 确认论文并指定刊期

```text
确认精读【论文标题 / DOI 列表】，整理到【YYYY-MM-DD】这一期，
时区是【时区】。刊期是网站归档日期，请保留各论文真实发表和版本日期。
先读全文及相关方法，再写独立精读页和简短日报摘要。
原文读不到的列出缺口，我可以上传 PDF；不要把摘要简报算成完整精读。
完成内容草稿和可检查的预览，暂不发布。
```

不要只给“今天”而不说明时区；历史补录也应使用明确日期。对长期有效但较早的论文，要求页面明确标注“方法补读”。

### 补充全文或更新预印本版本

```text
附件是【论文标题】的【v3 / 正式发表版】全文，
对应页面是【自己的页面 URL 或 paper ID】。
先核对标题、DOI、版本与日期，比较当前页面依据的版本。
根据附件更新方法、数据、关键结果、局限与图表；保留可追溯的更新说明。
不要混用旧版图号与新版结论，保持已有页面地址稳定。
请列出实质变化，再交付待审修改。
```

如果只想纠正一处数字，也应给出页码、图号或表号，让它核对数字对应的分析对象、单位和条件。

### 整理自己的数据资源目录

```text
请整理【领域】中用于【具体任务】的数据资源，优先从这些来源出发：
【综合目录、原始数据仓库、数据库论文或我提供的清单】。
资源比较维度是【字段列表】。独立样本单位是【单位】，
请与记录数、图像数、细胞数、时间点数等区分。
逐项核对原始入口、发布版本、实际分析规模、访问条件和许可证；
没有证据的字段写未核实。标明来源覆盖范围，不宣称已经穷尽。
先去重并交付候选表，确认后再接入页面和搜索。
未经我授权，不上传本地原始数据，也不把未确认条目放入公开资源 JSON。
```

领域迁移时，字段应服务于读者的选择。例如材料资源可能需要实验条件，语言资源可能需要语种与标注方式；不适用的字段应移除，而不是填进 QTL 的 donor 或 ancestry 字段。

### 审阅完成，明确授权发布

```text
我确认本次【刊期 / 论文 / 资源清单】及刚才展示的修改。
请发布到我的仓库【owner/repo】、生产分支【branch】，
部署到【自己的托管项目与域名】。
将本次确认的论文和刊期设为 published: true，核对引用和数量，
加入已确认的数据资源，完成构建并检查最终 diff。
然后提交并发布；核实 CI、托管部署状态和线上对应页面。
如果有实际失败，修复本次改动引起的问题，说明仍未解决的阻塞。
保持其他草稿状态，不开启定时任务。
```

这条指令只在你已经审阅结果后使用。对本仓库的 Cloudflare 配置，推送到 `master` 会触发生产构建，因此“写进生产分支但先不上线”不是独立步骤。

### 日常更新与移除无关文章

```text
按现有研究画像找【YYYY-MM-DD】这一期的候选，
时区【时区】，优先最近【N】天，查重后给出相关性与原始来源。
没有合适的新论文就说明，不凑数。先让我确认，再写入和发布。
```

```text
【页面 URL / paper ID】不符合【具体研究问题】，请从我的网站移除。
同步清理刊期引用、摘要、导航和搜索结果，检查篇数；
图片仅删除已无其他页面使用的文件。
把这次排除理由记入选题规则，并完成检查后发布这一项删除。
```

“每日网站”和“定时自动运行”是两件事。想自动化时，应另外明确频率、时区、候选送审方式和是否允许发布，并检查实际调度器状态；仅修改仓库文档不会创建或停用外部任务。

### 换一个对话继续维护

```text
继续维护我的网站【仓库 URL】。
请先读 AGENTS.md、研究画像、选题说明、最近提交和未完成的草稿／PR，
核对当前生产分支与部署状态。以仓库中最新规则和我的本轮指示为准。
本次任务是【具体更新】；不要重新初始化站点或覆盖已有历史。
先告诉我你识别到的当前状态，再完成已授权的工作。
```

## 4. 跨领域迁移要修改哪些地方

以下路径对应当前仓库。让 Astra 先检查实际代码再修改，迁移后应同步更新这份路径说明。

| 迁移对象 | 文件或目录 | 需要做什么 |
| --- | --- | --- |
| 研究画像与写作标准 | `src/data/research-profile.json`、`AGENTS.md`、`docs/selection-guide.md`、`docs/selection-and-review.md` | 替换领域、正反例、语言和来源偏好；不要原样继承站主的个人术语禁用规则 |
| 主题体系与内容字段 | `src/data/topics.ts`、`src/content.config.ts` | 使用自己领域的主题及稳定 slug；同步内容中的 topic 引用 |
| 论文与刊期 | `src/content/papers/`、`src/content/daily/` | 创建自己的内容，明确处理 fork 的演示条目；保留已有个人历史 |
| 数据资源模型 | `src/data/qtl-resources.json`、`src/data/qtl-groups.ts`、`src/data/qtl-ancestries.ts` | 重设分类、规模单位与筛选字段；需要重命名时同步全部导入 |
| 资源展示 | `src/components/QtlResource.astro`、`src/components/QtlDirectory.astro`、`src/pages/resources.astro` | 页面标签、筛选器和详情必须与新 schema 一致 |
| 搜索 | `src/lib/search-data.ts`、`src/lib/search.ts`、`src/pages/search.astro` | 更新资源字段、检索提示和词汇；更换语言时检查分词与匹配 |
| 站点身份和链接 | `astro.config.mjs`、`src/layouts/Base.astro`、`src/pages/index.astro`、`src/pages/rss.xml.js`、`public/favicon.svg` | 更换站名、域名、描述、仓库链接与图标，并搜索其他页面中的旧引用 |
| 图表与旧文章兼容 | `public/figures/`、`src/data/figure-overrides.json`、`src/plugins/remark-clean-headings.mjs`、`src/plugins/remark-review-figures.mjs` | 检查遗留图表覆盖和标题改写；新内容优先显式插图标记 |
| 构建与验收 | `scripts/check-content.mjs`、`scripts/validate-site.mjs`、`scripts/check-search.mjs`、`.github/workflows/` | 用新领域的真实内容替换硬编码样例；保留通用检查，核对分支触发条件 |

特别注意以下实现约束：

- **发布状态是关联的。** 论文需要自身已发布，并被已发布刊期引用，才进入公开目录；参考 `src/lib/catalog.ts`。论文 ID 使用小写，刊期篇数从引用数组导出，不另写一份数量。
- **正常预览不会自动显示草稿。** 目录和图表缓存脚本都跳过未发布刊期及论文。审阅新稿时，可在不提交、不推送的隔离本地副本中临时启用本次论文与刊期后构建；工作分支保留草稿状态。也可以实现受控的草稿预览模式，确保草稿不进入生产页面、搜索和 RSS。
- **资源没有逐条草稿过滤。** 当前资源 JSON 的记录会进入资源页和搜索。论文的 `published: false` 机制不能直接套用于资源；应隔离资源草稿或实现发布过滤。
- **不能直接删掉所有示例再期待构建通过。** `validate-site.mjs` 目前包含特定历史刊期、篇数、论文 ID、双图／公式和资源简报断言；`check-search.mjs` 包含 ColocBoost、TenK10K、BBJ 等领域用例。同步换成自己内容的正例、反例和日期，保留链接、图片、公式、草稿排除、排序、锚点和输入安全检查。
- **原文图需要真实资源。** 使用 `[[figure:figN]]`，其中 ID 对应文章的 `figures[].id`。当前 `scripts/cache-review-figures.mjs` 的自动下载来源限于配置中的 Nature / Springer 域名；其他出版商的图片不能假设会自动下载。准备核实过的本地原图，或针对实际来源调整下载规则并验证，不放宽为任意来源。
- **代码许可和内容许可分别处理。** 保留仓库 [LICENSE](../LICENSE) 和现有版权声明；论文原图与数据按各自来源的复用条件处理。
- **不需要把 Astra 接进网站运行时。** 当前网站构建后输出静态页面与搜索索引，访客浏览不调用模型；模型用于研究和维护。不要为复现现有功能额外引入在线模型接口或在前端放置密钥。

## 5. 构建、预览与上线验收

在自己的仓库工作目录中，使用 Node.js 22：

```bash
npm ci
npm run build
npm run preview
```

`npm run build` 会自动运行前后置脚本，覆盖内容检查、配置图表缓存、Astro 类型检查、静态构建、输出验证及搜索验证。预览地址以终端输出为准；让 Astra 检查实际页面，而不是只看源码。

上述命令预览的是构建产物，不会绕过发布过滤。检查尚未发布的新稿时，应先按上一节准备隔离的本地预览副本，再在该副本运行这些命令。发布前回到正式工作分支，在获得授权后设置发布状态并重新构建。

可以用这段话要求它交付：

```text
请交付本次修改的文件和内容摘要、原始来源、待确认项与检查结果。
确认论文和数据属于我的研究范围，版本与日期可追溯，
日报引用、篇数、主题、搜索结果、图片、公式和手机布局正常。
确认旧站身份与领域示例已按约定处理，其他历史内容和草稿没有被覆盖。
分别报告：构建结果、页面检查结果、GitHub 提交状态、托管部署状态；
未执行的检查或未验证的上线状态明确说明。
```

部署到自己的 Cloudflare Pages 项目时，连接自己的 GitHub 仓库，设置相应生产分支、构建命令 `npm run build` 和输出目录 `dist`，再配置自己的域名。Fork 不会自动继承原站的托管连接或域名。

本仓库的 [build workflow](../.github/workflows/build.yml) 验证面向 `master` 的 PR，以及匹配分支规则的 push；任意新分支不一定触发检查。另有历史 [research-review workflow](../.github/workflows/research-review.yml)，迁移时应检查它的分支配置。目标仓库使用其他生产分支时，要同步调整 CI 和托管设置。部署完成仍需核对线上页面，CI 成功不能替代托管平台的部署结果。

## 6. 为什么这样写 Prompt

给 Astra 明确的目标、依据、交付物、可自主完成的范围和需要你确认的节点；给科研筛选提供正反例；给代码迁移提供实际文件和验收标准。这样你能逐步修正方向，也能在下一次对话中从仓库继续维护。

关于 Astra 的通用提示词建议，可参考 [OpenAI：Using GPT-6 Astra](https://developers.openai.com/api/docs/guides/latest-model)。其中强调明确自主执行范围、检查 `AGENTS.md` 等指令文件、说明写作风格，以及让验证与任务规模相称。本指南中的领域迁移表和对话模板依据本仓库实现编写。
