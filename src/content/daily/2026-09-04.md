> **今日编辑判断**：优先读 **GLORB** 与 **SCALE**。GLORB 的关键不是换一种 normalization，而是承认相对计数无法自动区分技术测序深度与真实 global RNA shift；SCALE 的关键不是生成更漂亮的虚拟细胞，而是把预测对象明确为未配对 control/treated populations 间的条件分布。AnnFlux 的 neural SDE 表述很有吸引力，但阅读时必须追问 drift 与 diffusion 在稀疏时间点下是否可辨识。

## 三篇论文怎样串起来看

| 论文 | 主要 estimand | 最重要的统计单位/假设 | 阅读重点 |
|---|---|---|---|
| GLORB | 全局表达偏移下的 gene-specific differential effect | 相对计数中的 scale identifiability | 哪些先验或锚点把技术尺度与生物尺度分开 |
| SCALE | 给定 control set 与 perturbation 后的 treated-cell distribution | control 与 treated cells 未逐一配对 | endpoint prediction 与真实 trajectory 的区别 |
| AnnFlux | 扰动条件下潜在状态分布的连续时间演化 | 时间点/实验重复，而不是模拟轨迹数 | drift–diffusion identifiability 与 unseen-object extrapolation |

三者共同提醒：方法论文首先要明确**观测数据能识别什么**，然后才讨论网络结构和 benchmark。一个更复杂的生成模型并不会自动修复不可识别的 estimand；一个更稳健的 variance estimator 也不会自动修复 mean model 或设计混杂。

## Resource Watch · GWAS Catalog REST API v2

这不是 9 月 4 日当天的新 release，而是 **2026-08-19** 发布的迁移指南；由于它会直接影响自动化下载和资源监测，仍值得列入本期。

值得注意的变化包括：

- API 路径升级到 v2，并以 resource-based filtering 取代旧式搜索模式；
- 查询参数统一为 `snake_case`；
- 新增或强化 genes、publications、ancestries 等资源；
- ontology trait 查询可选择包含 child traits；
- `extended_geneset` 等参数的行为需要按 v2 文档重新核对；
- 分页响应和 rate limit 应在脚本中显式处理；官方指南给出的公开限制为每秒 15 个 queries。

对于本站后续自动化，迁移时不应只替换 base URL。需要建立 schema test：固定一组 known studies/traits，每次 API 变更后检查返回字段、分页总数和 filters 是否保持预期。

## 算法加速观察

SCALE 同时报告了训练 epoch time、iteration throughput 与 cells/s。修订版中的数字提示一个常见问题：按 epoch time 或 iterations/s 看起来可超过 10 倍，但在 effective batch/cells processed 不同的情况下，较公平的 **cells/s 端到端吞吐增益约为 1.29 倍**。

因此本站以后将原来的“GPU / HPC Watch”改为 **算法加速观察**，只关注：

1. 加速的是哪个算子或 pipeline stage；
2. 比较是否固定了处理的数据量与数值精度；
3. CPU–GPU 搬运、稀疏转稠密和 I/O 是否计入；
4. wall-clock、throughput、memory 与统计质量是否同时报告；
5. 并行化增益是否来自更多硬件，而非更高算法效率。

本日没有发现需要单独收录的全新 GPU-single-cell 软件 release；不以旧版本更新凑数。
